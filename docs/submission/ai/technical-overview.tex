\section{Summary}
Large language models can draft X3D quickly, but on their own their output is unreliable: invented field names, misplaced nodes, broken ROUTEs, mixed-up versions, and no way to see what they produced. This prototype takes a different route from ``a bigger model or a longer prompt'': it \textbf{grounds the model in the standard itself} (the ISO/IEC 19775-1 X3D Unified Object Model, compiled into a queryable database) and \textbf{closes the loop with verification the model cannot bypass} (the official X3D~4.0 XML Schema, a semantic linter derived from the object model, the X\_ITE runtime, and a screenshot the model inspects). The result is AI-generated 3D content that is \emph{standards-conformant by construction}, produced inside a complete browser-based X3D editor with live rendering, direct manipulation and multi-format import. Everything runs client-side as a static site; the only network traffic is the model call, made with the user's own key.

\section{How the AI is integrated} \crit{AI Integration 20\%}
\textbf{Models.} Google Gemini (3.8~Flash by default; 3.1~Pro and 2.5 selectable) and Anthropic Claude (Opus~5, Sonnet~5, Haiku~4.5), through their official JavaScript SDKs, directly from the browser. A small provider interface isolates each SDK in an adapter of about 150 lines, so the architecture is model-agnostic. Streaming, native function calling, images returned inside tool results (so the model can see its render) and effort/thinking controls are used where the provider supports them.

\textbf{The loop.} The model never writes to the scene directly. A provider-neutral agent loop sends the system prompt, the tool definitions and the conversation; executes the returned tool calls locally; appends their results; and repeats (up to 24 rounds per user turn). Seven tools:
\begin{itemize}
\item \texttt{get\_scene}, \texttt{edit\_scene} (exact, unique text replacements or anchored insertions; ambiguous edits are rejected), \texttt{replace\_scene}, \texttt{validate\_scene} -- each returns the full graded issue list with line numbers plus the X\_ITE render status, so the model repairs its own mistakes before answering;
\item \texttt{lookup\_node}, \texttt{search\_nodes} -- read the ISO object model: every field with type, accessType, default, accepted node types and containerField, the component and the specification URL; nodes the running X\_ITE build does not implement are flagged;
\item \texttt{screenshot} -- returns the current frame as an image so the model can check framing, lighting and visibility.
\end{itemize}
The system prompt is deliberately short: it fixes the workflow (read before edit, prefer patches, fix errors before answering, look up when unsure, screenshot when appearance matters) and a compact X3D~4.0 authoring guide. Correctness comes from the tools, not from prompt text. A per-message note carries the user's current selection, so deictic requests (``make \emph{this} twice as big'') resolve to an exact node.

\section{Verification stack} \crit{Technical Excellence 25\%}
\begin{enumerate}
\item \textbf{XSD}: the official \texttt{x3d-4.0.xsd} (with the Web3D extension schemas and the W3C XML-Signature schema it imports) is vendored and compiled once by libxml2 running in WebAssembly; validating a typical scene takes a few milliseconds.
\item \textbf{Semantic linter}: about thirty rules the schema cannot express, all driven by the object-model database: duplicate DEF, undefined USE, USE of a different node type, ROUTE to an unknown node or field, ROUTE from a non-output or to a non-input field, ROUTE type mismatch, a node in a parent field that does not accept it, several children in an SFNode field, attribute arity/type/range checks, zero rotation axes, interpolator key/keyValue consistency, empty groups, Shape without geometry, missing Viewpoint, unknown nodes and fields with did-you-mean suggestions, and nodes unsupported by the running X\_ITE build.
\item \textbf{Runtime}: X\_ITE parse errors and console warnings (missing textures, bad URLs, unsupported profiles) are captured during load and reported.
\end{enumerate}
Schema messages that duplicate a linter finding on the same line are demoted so the model is not double-penalised. The three layers are independent modules with a shared issue format, and the spec database is regenerated from the X3DUOM by a script.

\section{Web3D frameworks and standards}
X3D~4.0 (ISO/IEC 19775-1:2023) and its XML encoding (ISO/IEC 19776-1); the X3D Unified Object Model 4.0 (Web3D Consortium), compiled at build time into a database of 260 concrete nodes, 78 abstract types and 17 statements; X\_ITE~16.3 as rendering and runtime engine, including its glTF/OBJ/STL/PLY/SVG loaders and its XML/Classic VRML/JSON encoders (imports are normalised to X3D~4.0); CodeMirror~6 for the editor, with completions generated from the object model. All scenes the tool produces are plain, portable \texttt{.x3d} files; the gizmo, the selection sensors and everything else the tool adds at runtime live only in the X\_ITE scene graph and never enter the user's file.

\section{User experience} \crit{User Experience 15\%}
Zero installation: open a URL. Natural-language authoring with visible, expandable tool steps, so the user always knows what the model read, changed and verified. Direct manipulation with an X3D-native gizmo and a numeric inspector, synchronised two-way with the source; the text cursor selects nodes in the view and vice versa. Errors are phrased as actions (``\texttt{<Material>} goes inside \texttt{<Appearance>}''), with did-you-mean suggestions and jump-to-line. Eight example scenes, including one authored entirely through the copilot in four sentences (the snowman above) and a deliberately broken one for trying the repair loop.

\section{Why we think it is novel} \crit{Innovation \& Originality 30\%}
To our knowledge this is the first X3D authoring tool in which an LLM (a)~reads node and field definitions from the ISO object model through a tool instead of relying on training memory, (b)~can only act through validated edits whose reports are fed back to it, and (c)~inspects a screenshot of its own render before answering; and the first browser X3D editor whose transform gizmo is expressed in X3D sensor nodes. None of the individual ingredients is new; the contribution is the combination, and the fact that it makes AI-generated X3D conformant by construction rather than by luck. We have measured this informally rather than with a benchmark: in our recorded sessions the model repairs the eleven-error scene in one turn and builds complete animated, interactive scenes (nested orbits, sensors, PBR materials, shadows, click behaviours) from short prompts, and we ship those scenes as examples.

\section{Impact and scalability} \crit{Impact \& Scalability 10\%}
For the Web3D community the tool lowers the entry barrier to X3D to a sentence in a chat box while \emph{raising} conformance, which helps education, rapid prototyping and the health of the standard. The pattern (machine-readable specification + validators as tools + visual check) is not specific to X3D: the object-model database is generated by a script, and the same architecture applies to glTF, USD or CityGML with a different schema and object model. Scalability is trivial in the deployment sense, since the tool is a static site and the compute is the user's browser plus their own model account. Everything is open source under the MIT license, covered by 56 automated tests (schema fixtures, one test per linter rule, edit-tool patching, gizmo/source-map maths, and a check that every shipped example is lint-clean and schema-valid), with continuous integration on GitHub.

\section{Limitations}
Selection targets \texttt{Transform} nodes only; ProtoInstance internals are not selectable. The screenshot check is qualitative and the model's judgement of aesthetics varies between runs. Long generations depend on the provider's speed and quotas. Planned next steps: HAnim-aware tools (joint lookup, motion import), glTF export through X\_ITE, a retrieval tool over the X3D examples archive, and a quantitative evaluation of first-pass validity with and without the spec tools.
